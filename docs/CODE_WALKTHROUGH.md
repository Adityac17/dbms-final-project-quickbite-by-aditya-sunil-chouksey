## 1. `run_all.sh`

A Bash script that rebuilds everything with one command.

| Line | Code | Explanation |
|---|---|---|
| 1 | `#!/usr/bin/env bash` | The "shebang". It tells the OS to run this file with Bash, found through `env` so it works on any machine. |
| 2–3 | `# Builds the QuickBite…` | Comments: what the script does and how to run it. |
| 4 | `set -euo pipefail` | Safety switches. `-e` stops at the first failing command. `-u` makes an undefined variable an error. `-o pipefail` makes a pipeline fail if *any* part of it fails, not only the last. |
| 6 | `DB="${DB:-quickbite}"` | The database name. Uses the `DB` environment variable if you set one, otherwise `quickbite`. That's why `DB=mydb ./run_all.sh` works. |
| 7 | `cd "$(dirname "$0")"` | Moves into the folder the script lives in, so the relative paths like `sql/…` work from anywhere. |
| 8 | `mkdir -p outputs` | Creates `outputs/`. `-p` means no error if it already exists. |
| 10 | `PSQL=(psql -X -q -v ON_ERROR_STOP=1 -d "$DB" -P pager=off)` | Stores the psql command, with its options, in an array so it's typed once. `-X`: ignore your personal `~/.psqlrc`. `-q`: quiet. `ON_ERROR_STOP=1`: abort the file on the first SQL error, instead of carrying on. `-d`: which database. `pager=off`: print everything, never open `less`. |
| 12 | `echo "==> Recreating…"` | Progress message. |
| 13 | `dropdb --if-exists "$DB"` | Deletes the old database, if one exists, so every run starts clean. ⚠️ This erases anything in a DB of the same name. |
| 14 | `createdb "$DB"` | Creates a fresh, empty database. |
| 16 | `"${PSQL[@]}" -f sql/01_schema.sql` | Runs the schema file. `"${PSQL[@]}"` expands the array from line 10. |
| 17 | `… -f sql/02_indexes.sql` | Creates the indexes. |
| 18 | `… -f sql/03_seed_data.sql > /dev/null` | Loads the data. Its output (the `setval` numbers) is thrown away into `/dev/null`. |
| 20–28 | `"${PSQL[@]}" -c "SELECT 'restaurant' … UNION ALL …"` | One query that counts the rows in every table. `UNION ALL` stacks the seven `COUNT(*)` results into one table. `\| tee outputs/00_row_counts.txt` shows the result on screen **and** saves it to a file. |
| 30–35 | `… -f sql/04_queries.sql > outputs/04_queries_output.txt 2>&1` | Runs the queries, the index demo and the integrity tests. Each one's output is saved to a file. `2>&1` also captures error and notice messages (stderr), which is where the integrity test results are printed. |

### The trigger (lines 138–159)

**Why it exists:** an FK can check that a dish exists. It **can't** check that the dish belongs to the *same restaurant as the order*. Copying `restaurant_id` into `order_item` would make that check possible, but it would break 2NF, so a trigger does the check instead.

| Line | Code | Explanation |
|---|---|---|
| 143 | `CREATE OR REPLACE FUNCTION trg_order_item_same_restaurant()` | Defines a function. `OR REPLACE` lets the file be re-run. |
| 144 | `RETURNS TRIGGER AS $$` | A special return type for trigger functions. `$$` starts the function body (dollar-quoting, so there's no need to escape `'` inside). |
| 145 | `BEGIN` | Start of the PL/pgSQL code block. |
| 146 | `IF (SELECT restaurant_id FROM menu_item WHERE menu_item_id = NEW.menu_item_id)` | Looks up which restaurant **the dish** belongs to. `NEW` is the row being inserted or updated. |
| 147 | `IS DISTINCT FROM` | Like `<>`, but NULL-safe. `NULL <> 5` gives NULL, which an IF treats as false and would let a bad row through. `IS DISTINCT FROM` gives TRUE. |
| 148 | `(SELECT restaurant_id FROM food_order WHERE order_id = NEW.order_id) THEN` | Looks up which restaurant **the order** is from. |
| 149–151 | `RAISE EXCEPTION 'Menu item % does not belong…', NEW.menu_item_id, NEW.order_id;` | If they differ, abort with a clear message. Each `%` is replaced by the values that follow. |
| 152 | `END IF;` | End of the condition. |
| 153 | `RETURN NEW;` | If the check passes, return the row, which lets the insert go ahead. |
| 154–155 | `END; $$ LANGUAGE plpgsql;` | End of the function. It's written in PL/pgSQL, PostgreSQL's procedural language. |
| 157 | `CREATE TRIGGER order_item_same_restaurant` | Attaches the function to the table. |
| 158 | `BEFORE INSERT OR UPDATE ON order_item` | Runs **before** the row is saved, so a bad row never lands. |
| 159 | `FOR EACH ROW EXECUTE FUNCTION trg_order_item_same_restaurant();` | Runs once for every row affected. |

## 3. `sql/02_indexes.sql`

| Line | Code | Explanation |
|---|---|---|
| 5–14 | comment | Explains the index and **why the column order matters**. |
| 15–16 | `CREATE INDEX idx_restaurant_cuisine_location ON restaurant (cuisine, location);` | **The advanced concept.** It's a B-tree index sorted by cuisine, then by location, like a phone book sorted by surname then first name. A search for `cuisine='X' AND location='Y'` jumps straight to the matching entries instead of reading every row. |
| 18–23 | comment | PostgreSQL does **not** automatically index FK columns, unlike MySQL/InnoDB. |
| 24 | `CREATE INDEX idx_menu_item_restaurant ON menu_item (restaurant_id);` | Speeds up "all dishes of restaurant X" and the JOINs that use it. |
| 25–27 | `… food_order (restaurant_id)`, `(customer_id)`, `(delivery_agent_id)` | Speeds up joins from orders to each parent, and the RESTRICT check when someone tries to delete a parent. |
| 28 | `… order_item (menu_item_id)` | `order_item.order_id` doesn't need its own index, because it's the **first** column of the composite PK, which is already an index. `menu_item_id` is second, so it gets one. |

**The leftmost-prefix rule:** the index on `(cuisine, location)` helps searches on `cuisine` alone and on `cuisine + location`. It can't seek on `location` alone, for the same reason a phone book sorted by surname can't find everyone named "Rahul" quickly.

### Orders (lines 134–194): `INSERT … SELECT … FROM (VALUES …) JOIN`

```sql
INSERT INTO food_order (order_id, customer_id, …, delivered_time)   -- 134-135 target columns
SELECT v.oid, v.cid, v.rid, v.aid,                                  -- 136 copy ids from the list
       v.t::TIMESTAMP,                                              -- 137 text → timestamp
       c.address,                                                   -- 138 address FROM the customer table
       v.st,                                                        -- 139 status
       CASE WHEN v.mins IS NULL THEN NULL                           -- 140 not delivered → no time
            ELSE v.t::TIMESTAMP + make_interval(mins => v.mins) END -- 141 delivered = ordered + N minutes
FROM (VALUES                                                        -- 142 an inline table
 ( 1,  1,  1, 1, '2026-09-02 13:05', 'Delivered', 34),              -- 144 one order per line
 …
) AS v(oid, cid, rid, aid, t, st, mins)                             -- 193 name the inline table + its columns
JOIN customer c ON c.customer_id = v.cid;                           -- 194 look up each customer
```

**Why this pattern:** `delivery_address` is copied from the customer **by the database**, not retyped, so there are no typos. The delivered time is *calculated* from minutes, so it's always after the order time and never trips the CHECK constraint. Line 159 (order 16) and the line for order 47 are `Cancelled` with `NULL` minutes. Orders 48–49 are still in progress.

### Order lines (lines 199–262)

```sql
INSERT INTO order_item (order_id, menu_item_id, quantity, unit_price)
SELECT v.oid, v.mid, v.qty, m.price          -- 200 price copied from the menu at "order time"
FROM (VALUES ( 1, 1,1),( 1, 4,4), … )        -- each (order, dish, qty)
AS v(oid, mid, qty)
JOIN menu_item m ON m.menu_item_id = v.mid;  -- 262 look up the price
```

`( 1, 4,4)` means "order 1 contains dish 4 (Butter Naan) × 4". The **Dragon Wok** block (orders 12–16) is built so that *Veg Hakka Noodles* and *Chilli Paneer* tie at 3 orders each. That tests whether Q1 handles ties. Every line also passes through the trigger, so a wrong restaurant would make the whole load fail.

### Payments (lines 267–295): three `CASE` expressions

| Lines | Column | Rule |
|---|---|---|
| 270–274 | `status` | Cancelled order → `Refunded`. Cash and not yet delivered → `Pending`. Anything else → `Paid`. |
| 275–277 | `transaction_ref` | Cash → NULL. Otherwise `'QB'` + date + 5-digit order number, e.g. `QB2026090200001`. `\|\|` joins strings, and `lpad(…, 5, '0')` pads the number with zeros. |
| 278–281 | `paid_at` | Cash is paid when delivered. Online payments are made 1 minute after ordering. |

### Resetting the ID counters (lines 297–306)

```sql
SELECT setval(pg_get_serial_sequence('restaurant','restaurant_id'), (SELECT MAX(restaurant_id) FROM restaurant));
```

Because we inserted explicit IDs, the auto-numbering counter is still at 1. Without this line, the next *app* insert would try ID 1 and crash with a duplicate-key error. `pg_get_serial_sequence` finds the counter behind the column, and `setval` moves it to the current maximum. `order_item` has no line here, because it has no identity column.

## 5. `sql/04_queries.sql`

**Lines 1–6** set one business rule for every query: *cancelled orders aren't demand, and only delivered orders count as revenue*. Each query is preceded by `\echo` lines. These are **psql commands**, not SQL. They print a banner into the output file.

### Q1. Most popular dish per restaurant (lines 8–37), the query the brief requires

| Line | Code | Explanation |
|---|---|---|
| 14–18 | `SELECT r.restaurant_id, r.name AS restaurant, m.name AS most_popular_dish, COUNT(*) AS times_ordered, SUM(oi.quantity) AS units_sold` | `COUNT(*)` = how many orders included this dish. `SUM(quantity)` = how many plates were sold. `AS` renames the column in the output. |
| 19 | `FROM order_item oi` | Start from the order lines, where "dish was ordered" facts live. |
| 20 | `JOIN menu_item m ON m.menu_item_id = oi.menu_item_id` | **The required JOIN** between order lines and MenuItem, to get the dish name and its restaurant. |
| 21 | `JOIN food_order fo ON fo.order_id = oi.order_id` | Needed to read the order's `status`. |
| 22 | `JOIN restaurant r ON r.restaurant_id = m.restaurant_id` | Gets the restaurant's name. |
| 23 | `WHERE fo.status <> 'Cancelled'` | Drops cancelled orders *before* counting. |
| 24 | `GROUP BY r.restaurant_id, r.name, m.menu_item_id, m.name` | One group per (restaurant, dish). Every non-aggregated column in `SELECT` must appear here. |
| 25 | `HAVING COUNT(*) = (` | Keeps only groups whose count equals the value from the subquery below. `HAVING` filters *groups*, while `WHERE` filters *rows*. |
| 28 | `SELECT MAX(dish_count)` | **The ranking subquery.** It finds the highest dish count… |
| 29–35 | `FROM (SELECT COUNT(*) AS dish_count FROM order_item oi2 JOIN … WHERE m2.restaurant_id = r.restaurant_id AND … GROUP BY oi2.menu_item_id) AS per_dish` | …among the dishes **of this restaurant only**. `m2.restaurant_id = r.restaurant_id` refers to `r` from the *outer* query, which makes this a **correlated subquery**: it re-runs once per outer group. The inner aliases (`oi2`, `m2`, `fo2`) must differ from the outer ones. |
| 37 | `ORDER BY r.restaurant_id, m.name;` | Sorts the output. |

**Tie handling:** if two dishes both equal the max, *both* pass the HAVING, which is why Dragon Wok appears twice.

### Q1b. The same result with window functions (lines 40–67)

| Line | Code | Explanation |
|---|---|---|
| 45–54 | `WITH dish_stats AS (SELECT … GROUP BY …)` | A **CTE** (Common Table Expression), a named temporary result. It holds counts and units per dish, the same numbers as Q1. |
| 55–61 | `ranked AS (SELECT ds.*, RANK() OVER (…), ROW_NUMBER() OVER (…))` | A second CTE that builds on the first. |
| 57 | `RANK() OVER (PARTITION BY restaurant_id ORDER BY times_ordered DESC)` | A **window function**. `PARTITION BY` restarts the ranking for each restaurant, and `ORDER BY … DESC` gives the highest count rank 1. Ties share a rank (1, 1, 3…). Unlike `GROUP BY`, a window function keeps every row. |
| 58–59 | `ROW_NUMBER() OVER (… ORDER BY times_ordered DESC, units_sold DESC, dish)` | Always gives 1, 2, 3, with no ties. Ties are broken by units sold, then alphabetically. This picks **exactly one** dish to promote. |
| 62–63 | `CASE WHEN promo_pick = 1 THEN 'YES' ELSE '' END AS promote` | Marks the chosen dish. |
| 65 | `JOIN restaurant r USING (restaurant_id)` | `USING` is shorthand for `ON ranked.restaurant_id = r.restaurant_id` when the column names match. |
| 66 | `WHERE popularity_rank = 1` | Keeps only the top dishes. You can't filter on a window function in the same SELECT where it's computed, which is why the CTE is needed. |

### Q2. Revenue per restaurant (lines 70–86), required outcome

| Line | Code | Explanation |
|---|---|---|
| 78 | `COUNT(t.order_id) AS delivered_orders` | `COUNT(column)` skips NULLs, so a restaurant with no orders gets **0**, not 1. `COUNT(*)` would give 1. |
| 79 | `COALESCE(SUM(t.order_total), 0) AS total_revenue` | **GROUP BY + SUM on order totals**, as the brief asks. `SUM` of nothing is NULL, and `COALESCE(x, 0)` turns NULL into 0. |
| 80 | `COALESCE(ROUND(AVG(t.order_total), 2), 0)` | Average bill, rounded to 2 decimals. |
| 81–84 | `FROM restaurant r LEFT JOIN v_order_total t ON t.restaurant_id = r.restaurant_id AND t.status = 'Delivered'` | **LEFT JOIN** keeps every restaurant, even ones with no matching orders. ⚠️ The status filter is in `ON`, **not** in `WHERE`. In `WHERE`, it would throw away the NULL rows and silently turn the LEFT JOIN into an INNER JOIN, and Malvani Tadka would disappear. |
| 85 | `GROUP BY r.restaurant_id, r.name, r.cuisine` | One row per restaurant. |

### Q2b (lines 89–101)
The same revenue, calculated straight from `order_item` (`SUM(oi.quantity * oi.unit_price)`) without the view. This proves the view is correct. It uses an **INNER JOIN** and the filter is in `WHERE`, so restaurants with no sales drop out (10 rows instead of 11). That's a good example of the LEFT vs INNER difference.

### Q3. Search by cuisine and area (lines 104–114)
`WHERE cuisine = 'North Indian' AND location = 'Kharghar' AND is_active` is exactly the search the index was built for. `AND is_active` is shorthand for `is_active = TRUE`. `ORDER BY rating DESC` puts the best-rated first.

### Q4. Above-average restaurants (lines 117–133)

| 127 | `HAVING SUM(t.order_total) > (` compares each restaurant's total… |
| 128–132 | …with `AVG(rest_rev)` taken over a **derived table** (a subquery in `FROM`, aliased `x`) that holds one revenue figure per restaurant. You need two levels because you can't nest aggregates, so `AVG(SUM(…))` isn't allowed. |

### Q5. Dishes never ordered (lines 136–150)
| Line | Explanation |
|---|---|
| 141–143 | Every dish, joined to its restaurant. |
| 144 | `WHERE NOT EXISTS (` keeps the dish only if the subquery finds **nothing**. |

### Q6. Delivery-agent performance (lines 153–169)
| Line | Explanation |
|---|---|
| 162 | `fo.delivered_time - fo.order_time` gives an *interval*. `EXTRACT(EPOCH FROM …)` converts it to seconds, `/ 60` to minutes, `AVG` averages them, and `ROUND(…, 1)` keeps 1 decimal. |

### Q7. Top 5 customers (lines 172–186)
Customer joined to `v_order_total`, delivered orders only, `GROUP BY` customer, `SUM` of spend, `ORDER BY … DESC`, and `LIMIT 5` keeps the first 5 rows.

### Q8. Revenue by cuisine (lines 189–201)
`COUNT(DISTINCT r.restaurant_id)` counts restaurants per cuisine **without duplicates**. A plain `COUNT` would count one per order row. LEFT JOIN + COALESCE keeps Malvani at 0.

### Q9. Invoice for order #26 (lines 204–226)
A **7-table JOIN**: `food_order → customer, restaurant, delivery_agent, order_item → menu_item, payment`. Line 209: `to_char(fo.order_time, 'DD-Mon-YYYY HH24:MI')` formats the date as `21-Sep-2026 20:45`. Line 216 calculates each line total. Line 225 picks one order.

### Q10. Payment-method split (lines 229–241)
Line 236, `ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1)`, is a window function **over an aggregate**. `COUNT(*)` gives this method's orders. `SUM(COUNT(*)) OVER ()` adds up all the groups' counts. An empty `OVER ()` means the window is the whole result. Writing `100.0` instead of `100` forces decimal division. Integer division would give `7/45 = 0`.

## 7. `sql/06_integrity_tests.sql`

| Line | Code | Explanation |
|---|---|---|
| 7 | `DO $$` | Runs an **anonymous code block**, i.e. procedural code without creating a function. |
| 8 | `DECLARE` | Variable declarations follow. |
| 9 | `tests TEXT[][] := ARRAY[` | A 2-D text array. Each entry is `[description, SQL to try]`. |
| 10–12 | `['Order for a customer that does not exist (FK)', $q$INSERT … VALUES (999, 1, 1, 'Nowhere')$q$]` | Customer 999 doesn't exist, so the FK should reject this. `$q$ … $q$` is a *named dollar quote*, used so the SQL inside can contain `'` and won't clash with the outer `$$`. |
| 13–15 | missing restaurant | Restaurant 999. Expect an FK error. |
| 16–18 | NULL delivery agent | Expect a NOT NULL error. |
| 19–21 | dish 21 (Biryani Darbar) on order 1 (Punjab Da Dhaba) | Expect **the trigger** to fire. |
| 22–23 | `DELETE FROM restaurant WHERE restaurant_id = 1` | Expect RESTRICT. Note that the `menu_item` FK is checked first and blocks the delete, before the `food_order` FK is reached. Either way, the restaurant is protected. |
| 24–25 | second payment for order 1 | Expect the UNIQUE (1 : 1) error. |
| 26–28 | price −10 | Expect a CHECK error. |
| 29–30 | status 'Lost' | Expect a CHECK error. |
| 31–33 | a duplicate email | Expect a UNIQUE error. |
| 35 | `i INT;` | The loop counter. |
| 37 | `FOR i IN 1 .. array_length(tests, 1) LOOP` | Loops over the 9 tests. `array_length(tests, 1)` is the size of the first dimension. |
| 38 | `BEGIN` | An **inner block**. An inner block with an `EXCEPTION` clause gets its own *savepoint*, so a failure here is undone without killing the loop. |
| 39 | `EXECUTE tests[i][2];` | Runs the SQL text. This is dynamic SQL. |
| 40 | `RAISE NOTICE 'FAIL … was accepted!'` | Only reached if the bad statement **succeeded**, which would mean a missing constraint. |
| 41 | `EXCEPTION WHEN OTHERS THEN` | Catches any error. |
| 42–43 | `RAISE NOTICE 'OK %' …; RAISE NOTICE 'rejected: %', SQLERRM;` | Prints a pass, plus the database's own error message. `SQLERRM` holds the text of the caught error. |
| 44–46 | `END; END LOOP; END $$;` | Close the inner block, the loop and the DO block. |

Because each failing statement is rolled back to its savepoint, **nothing changes in the database**. The final output is nine `OK` lines.
